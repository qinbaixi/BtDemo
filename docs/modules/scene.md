# 场景与分线：Scene、Manager、迁移

代码：`internal/game/scene.go`（一个场景）、`internal/game/manager.go`（场景管理器）、`internal/game/travel.go`（换场景、换线）、`internal/game/portal`（传送门）、`internal/game/session/travel.go`（会话交出 / 接收）。配置：`config/scenes.yaml`、`config/maps/*.tmj`。

设计的来龙去脉见项目文件里的 `btdemo/scene-lines-design.md`。

副本（`kind: dungeon` 的场景）不分线，每个进来的玩家单独开一份，见 [关卡](level.md)。

## 为什么要分

原来整个服务器只有一个 `World`，跑在一个 goroutine 上，最多用满一个核。现在 `World` 改叫 `Scene`，可以同时开很多个：

- **场景模板**（`scenes.yaml` 的一项）：一张地图加上地图上的怪物、回血区、出生点。现在有 `village`（晨曦村）和 `graveyard`（亡者墓园）。
- **线**：同一个模板可以同时开好几份，叫第 1 线、第 2 线……每条线是一个 `Scene`，各自一个 goroutine、各自的实体表、AOI 格子、寻路网格、随机数和时钟，**互不共享可变数据**。场景内部的代码和原来一样是单线程、不加锁的。
- 场景越多，能用的核越多。只读的数据（配置、编译好的行为树、地图）所有线共用一份。

## 结构

```text
浏览器 ──WebSocket──► server（每连接一个读协程 + 一个写协程）
                         │ Hello{token}
                         ▼
                  Manager（一把锁）
                  ├─ routes：token → 角色在哪条线（或者正在迁移）
                  ├─ village：第 1 线、第 2 线……
                  └─ graveyard：第 1 线……
                         │ scene.Do(func)
                         ▼
              Scene（每条线一个 goroutine，各自 tick）
```

### Manager 的规则

- Manager 的表只用一把锁保护。**拿着锁时从不等场景**，要场景做事一律 `scene.Do`（不阻塞）；场景可以随时同步调用 Manager 的方法（拿一下锁马上返回）。所以不会死锁。
- 每条线记一个 `residents`：属于这条线的角色数（在线上的、断线保留中的、正在过来的）。分线按它算，它为 0 的线才能关。

### 分线

`scenes.yaml` 的 `lines`（可以每个场景单独覆盖）：

| 字段 | 意思 |
| --- | --- |
| `soft` | 一条线的“满员”人数：超过它，新玩家优先去别的线，都超过了就开新线 |
| `hard` | 一条线最多多少人，到了就进不去（指定线号切线也不行） |
| `min` | 常驻的线数，没人也不关 |
| `idle_close` | 多出来的线空了多少毫秒后关闭（默认 120000） |

选线（`Manager.pick`）：指定了线号就去那条（不存在或满了就拒绝）；否则在没超过 `soft` 的线里选**人最多**的（让每条线都热闹），都超过了开新线，线号取最小的空号。Manager 每 5 秒检查一次，关掉空了太久的线（`closeIdle`）。

### 实体 ID 和时钟

- 所有场景共用一个 `core.IDSource`（原子计数），玩家、宠物换场景后 ID 不变，客户端和调试面板都只认 ID。
- 新开的线时钟从“服务器启动以来的毫秒数”开始（`core.NewSceneState` 的 start），各条线的游戏时间对得上。客户端按帧里的时间换算冷却和 Buff，换线时时钟不会跳。

## 换场景、换线（迁移）

核心原则：**任何时刻一个角色只有一个主人**：源场景 → 迁移途中的 Manager → 目标场景。不会两边都有（复制装备），也不会两边都没有（丢角色）。

```text
源场景（自己的 goroutine）                Manager（拿锁）            目标场景（自己的 goroutine）
1. 踩传送门 / 切线：检查活着、不在战斗中
2. 发 Travel（客户端显示过场）
3. 打包：清掉只属于这个场景的状态，冷却换成“还剩多少毫秒”
4. TakeOut：收回宠物，角色移出场景
5. depart ─────────────────────────────► 选目标线，角色进入迁移途中
6. target.Do(arrive) ─────────────────────────────────────────────► 7. arrived：角色归目标场景
                                                                    8. 冷却按新时钟还原，放到落点
                                                                    9. Bring：重新发全部东西
```

- **角色实体对象本身跟着走**：ID、等级、经验、背包、装备、技能、血量都不变。第 4 步之后源场景不再碰它。
- **清掉的**（`packPlayer`）：Buff 和减益、当前目标、仇恨（最近攻击者）、路径、按着的方向键、格挡。宠物在源场景收回，到目标场景由宠物系统重新召唤。
- **按新时钟还原的**：技能冷却、换宠物冷却。
- **会话对象也跟着走**：token、连接（`session.Link`）和输入队列（`session.Inbox`）不变，所以 **WebSocket 不用重连**。目标场景用同一个 Link 发新的 `Welcome{resumed, scene}`，客户端清空实体、按新地图重建场景。迁移途中客户端按的键在到达时整批作废。
- **落点**：换线落在原来的位置；换场景落在目标场景里通回来的那扇传送门外面（朝出生点挪开一点），没有通回来的门就落在出生点。

### 异常情况

| 情况 | 处理 |
| --- | --- |
| 指定的线满了、没有这条线 | 出发前检查，拒绝并提示；出发时刚好满了就改去别的线 |
| 迁移途中断线 | Manager 拿着锁把会话的连接置空；到了目标场景按断线保留处理（`session.keep` 毫秒内重连接回来） |
| 迁移途中重连 | Manager 把新连接换上去（旧连接关掉），到了目标场景按新连接发全量 |
| 重连时角色刚好离开了那条线 | 那条线发现角色不在，再问一次 Manager（`attach` 会重新找） |
| 目标场景已经停止（停服） | 删掉角色、断开连接 |

## 传送门

地图里 `portals` 图层的点对象（类 `portal`），属性 `to` 是目标场景 id，`r` 是半径（默认 36）。玩家（连着的、活着的）站进去 600 毫秒就出发（`portal.Dwell`），路过擦一下不会被传走。Welcome 的 `scene.portals` 把门的位置和去处发给客户端，前端画在 `web/src/render/portals.ts`。

## 协议

| 消息 | 方向 | 说明 |
| --- | --- | --- |
| `Welcome.scene` | 服务端 → 客户端 | 所在场景 id、名字、线号、地图地址（`/maps/village.tmj`）、传送门 |
| `ClientMsg.lines` / `LineList` | 双向 | 要这个场景的线路列表 / 每条线的人数和 soft、hard |
| `ClientMsg.switch_line` | 客户端 → 服务端 | 换到第几线；被拒绝时回 Toast |
| `Travel` | 服务端 → 客户端 | 正在前往某场景：显示过场，等下一个 Welcome |

HTTP：`/maps/<文件名>` 是各场景的地图（`/map.tmj` 是默认场景的，旧地址），`/debug/scenes` 列出每条线的人数、实体数和 tick 耗时（JSON）。

## 测试

`internal/game/manager_test.go`：不起 goroutine，用 `pump` 手动推进每条线，检查传送门迁移（同一个角色、Buff 清掉、冷却带过去、落点、宠物重召、周围的人看到离开）、分线和切线、空线关闭、迁移途中断线 / 重连；最后一个测试让所有线在各自的 goroutine 上跑、一批玩家同时来回切线和重连，用 `go test -race` 检查没有数据竞争。
